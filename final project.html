Vision-Based UAV Tracking Final Project

We built a MuJoCo simulation of a UAV tracking a moving platform with image-based visual servoing. The project focused on using camera feedback to compute tracking error directly in the image, convert that error into velocity commands, and test how the controller behaves under both clean and difficult scenarios.

Project Goal

The original idea was to create a vision-based autonomous UAV tracking system that could eventually move toward real hardware. We cared about a drone looking downward at a moving platform, detecting that target in the camera image, and using that visual information to stay over it.

We started in simulation first because it let us build the perception and controller loop in a controlled setting before trying to fight hardware integration, firmware restrictions, and flight safety at the same time.

Why IBVS

We used image-based visual servoing because it is a direct way to control motion from what the camera sees. Instead of requiring perfect world-position estimates, the controller uses image error from the target location in the frame.

In our setup, the red platform marker is detected in the onboard camera image. We define:

e_x = horizontal image error e_v = vertical image error v_x = k_x e_x v_y = -k_y e_v

If the target is centered in the image, then e_x = 0 and e_v = 0, so the command goes to zero. If the target moves away from the center, the drone is commanded to move in the direction that reduces that image error.

The negative sign on v_y comes from the fact that image coordinates grow downward while the simulation world y-axis grows upward.

What We Built

Simulation Side

  • MuJoCo scene with a moving platform and a simplified UAV.
  • Fixed external top-down camera for debugging.
  • Onboard downward-facing camera mounted under the UAV.
  • Generic quadrotor visual model so the UAV reads more like a drone.

Control Side

  • HSV color segmentation to detect the red platform marker.
  • Image error computation from the camera frame.
  • Proportional IBVS controller for planar motion.
  • Logging of error, commands, positions, and separation distance.

Problems We Ran Into

  • Image-to-motion sign and gain tuning: early versions drifted or moved the wrong way until the image axes were mapped correctly to simulation motion.
  • Camera setup: the onboard camera initially did not feel physically right, so we moved it underneath the UAV to better match the real use case.
  • Target dropouts: when the platform moved quickly or left the frame, the controller had to rely on held or decaying commands.
  • Clutter and ambiguity: once multiple red platforms were added, the simple color-based detector became much less reliable.
  • Controller complexity: we briefly looked at PID-style control, but it did not clearly outperform the simpler proportional IBVS baseline in the time available.
  • Hardware command path: the biggest real-world problem was not vision, but getting commands cleanly into the actual drone stack.

Hardware Attempt

We did spend time trying to move this toward hardware. We were able to get the camera and Raspberry Pi side far enough along to support the visual-tracking idea, but we ran into trouble on the control side.

The drone microcontroller and flight electronics were too embedded for us to cleanly port over the command interface in the time we had left. So while the visual side was promising, we could not reliably send the higher-level velocity commands into the drone stack.

What We Would Need To Do Next

  • Use a flight stack or SDK that clearly accepts high-level commands such as velocity setpoints.
  • Confirm whether the real drone expects body-frame or world-frame commands, then map the IBVS output into that frame.
  • Keep the onboard controller responsible for low-level stabilization such as roll, pitch, yaw, and thrust.
  • Add safety behavior for target loss, command saturation, and manual override.
  • Port the perception and controller modules onto the Raspberry Pi or companion computer in a clean runtime loop.
  • Test with real camera frames first, then command logging only, then small controlled motion.

The simulation work is still useful here because it already gives us the outer-loop structure: camera image → image error → velocity command. The missing part is the hardware command bridge.

Final Takeaway

The project ended with a working simulation baseline for vision-based UAV tracking. We built a complete loop that renders camera images, detects a target, computes image error, produces control commands, and evaluates the result under several scenarios.

We did not fully complete hardware deployment, but we did get far enough to understand where the actual barrier was: not the core visual tracking idea, but the interface between our controller output and the drone's embedded control stack.
