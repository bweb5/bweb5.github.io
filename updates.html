Simulation Progress (MuJoCo)

  • Built an initial MuJoCo simulation scene containing a UAV body, a moving ground platform, and a high-contrast marker.
  • Implemented a top-down “look-down” camera view using a Python-controlled MuJoCo camera (stable across MuJoCo versions).
  • Added basic marker detection using grayscale thresholding and contour detection.
  • Computed pixel error between the marker centroid and the image center, and mapped that error to simple planar command signals (not yet applied to UAV motion).
  • Validated real-time rendering and confirmed the moving platform and marker are consistently visible in the camera view.

Week 7 — 03/01–03/07

This week we moved the project from basic marker detection toward a more complete tracking loop. The goal was to make the simulation show a clear relationship between camera error and UAV motion.

Controller and Simulation Work

  • Added a fixed external camera view for debugging the UAV and platform positions.
  • Detected both the red platform marker and the blue UAV marker in the external camera image.
  • Computed relative image error between the platform and UAV centroids.
  • Used the image error to generate planar command signals for the UAV.
  • Continued logging image error, command output, and separation distance for later analysis.

Week 12 — 04/05–04/11

This week we reorganized the simulation into a clearer baseline system that can later be adapted for hardware. The simulation now separates perception, controller logic, MuJoCo interfacing, shared messages, and logging.

Baseline Visual Servo Controller

  • Implemented a proportional image-based visual servo controller using image error ex and ev.
  • Converted filtered pixel error into planar velocity commands vx and vy.
  • Defined a reusable velocity command output that can later map to a real UAV interface.

Simulation Updates

  • Added named MuJoCo cameras for the fixed external view and onboard downward UAV view.
  • Attached the onboard camera underneath the UAV body to better represent a real downward-facing camera.
  • Improved the marker geometry so the target remains visible from the camera views.
  • Verified both external-camera tracking and onboard-camera tracking in headless simulation runs.

Hardware Updates

  • Did more research into the MindRacer 210mm Racing Drone and the flight stack.
  • Downloaded the necessary tools for programming the drone and ground station.
  • We are using the MindRacer mainboard and are looking into a compnaion computer setup for our computer vision tasks (Raspberry Pi)

Week 13 — 04/12–04/18

Most of this week was spent reading the paper and preparing the presentation, so progress on the project itself was limited. We still spent some time reviewing the controller structure and briefly tested a simple PID version of the image-based controller, but the results were not clearly better than the simpler proportional IBVS baseline. Because of that, we kept the proportional controller as the main controller for the rest of the simulation work.

In short, this week was more about regrouping after the presentation and deciding to keep the project centered on a working simulation rather than trying to force a more complicated controller without enough tuning time.

Week 15 — 04/26–05/02

This week we extended the scenario testing to include clutter and target ambiguity. The goal was to see how a simple color-based IBVS system behaves when there are multiple red platforms in the scene instead of one clean target.

Clutter and Ambiguity Tests

  • Tested a case where two targets start together and then separate.
  • Added a moving-clutter case to make the detection problem less idealized.

Week 16 — 05/03–05/09

Around this week we also spent time trying to connect the simulation work back to the hardware direction of the project. This mostly meant reviewing the drone platform, flight stack, and what command interface would be needed if we wanted to move from simulation to a real system. We did not complete a hardware deployment, but we were able to keep the simulation code organized around a simple command output so that it could later be mapped to a real drone interface.

Finals week also limited how much deeper we could go, so the main result here was keeping the software work simulation-focused while still thinking through how it would translate to hardware later.
